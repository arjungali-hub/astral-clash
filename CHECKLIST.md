# Astral Clash — Build Brief Checklist

Tracks every item from the build-brief prompt. Updated after every batch of changes to `index.html`.

**Time-scaling approach (Batch 1 decision):** using the `dt` multiplier model (dt = 1.0 at 60fps), not a full frames→seconds conversion. Existing per-frame tuning constants stay valid multiplied by `dt`, rather than rewriting every constant into real-world units.

Legend: `[x]` done · `[~]` partially done (see note) · `[ ]` not started

## Regression found and fixed outside the batch list

**The game was completely unplayable after the previous update** — the fighter-select grids were empty and the Bot toggle button did nothing. Root cause: `onWindowResize()` was called immediately at setup time (to size the canvas on first load) but reads `camera`, which is a `const` declared *later* in the script — a temporal-dead-zone `ReferenceError` that threw before `buildGrid()` or the bot-toggle listener ever ran, silently halting the rest of the script. `node --check` never caught this because it only validates syntax, not runtime references — confirmed by actually executing the script under a mocked DOM/THREE harness. Fixed by moving the initial `onWindowResize()` call to after `camera` is constructed. This wasn't on the brief's list because it was introduced by the huge feature-update batch, not by anything the brief was written against — noting it here since it directly affects the "no console errors" verify item for every batch since.

**Special meter always showed NaN and never charged.** Root cause: `Fighter.meterRateMult` was read in two places (passive regen and on-hit meter gain, both part of Batch 4's unified meter-generation rework) but the constructor never actually assigned it from the character config — so it was `undefined`, `undefined * anything` is `NaN`, and once `specialMeter` went `NaN` it stayed `NaN` forever (any further arithmetic on a `NaN` is still `NaN`), which is exactly the "shows NaN and won't charge" symptom reported. This is a case the mock-DOM harness can't catch — `undefined * x` doesn't throw, it just silently produces `NaN`, so the script "ran fine" by the harness's own definition even with this bug present; it needed an actual human noticing wrong-looking output. Fixed by adding the missing `this.meterRateMult = cfg.meterRateMult;` in the constructor, alongside the other per-character stat assignments.

**Training mode removed at the user's explicit request** after being built in Batch 9 — see that batch's section below for what was deleted.

**Per-attack weapon animation added**, on request, beyond the whole-mesh lean Batch 8 shipped. Each character's mesh builder now stashes a `weapon` part (or parts — Voss's twin daggers move together) and a `weaponAnim` config; `initMesh()` captures each part's rest transform once, and a new `animateWeapon()` (called every frame from `render3D`, layered on top of the existing lean) drives a real per-character swing: Kaelen and Voss get a horizontal slash/stab arc (rotate around Y), Draven gets a heavy overhead swing (rotate around Z), Gorgonok gets a straight punch thrust (position offset along local X), and the two ranged casters (Lyra, Seraphine) get a charge-and-release scale pulse on their shard/halo instead of a melee swing, since they don't have a weapon part to swing. All three animation types share one generic startup→active→recovery progress curve (wind-up extreme → follow-through extreme → ease back to rest) rather than six bespoke per-character animation functions.

**The "skill" action (third attack, on top of basic/special) removed at the user's explicit request.** This was a bigger removal than it looks — every character had a unique skill (Kaelen's Twin Strike, Lyra's Glass Step, Gorgonok's Ground Pound, Voss's Smoke Step, Draven's Bulwark Stance, Seraphine's Radiant Pulse), so this touches most systems in the file: `CHARACTERS` config (`skill2Id`/`skill2Name`/`skill2Desc`/`skill2Cooldown` fields), `FRAME_DATA` (the `skill` startup/active/recovery sub-object per character), the whole `Fighter.doSkill()` method and its six-case switch, `tryStartAction`/`updateActionState`'s skill branches, `skill2Cooldown`/`skill2CooldownMax` fields and their per-frame tick, the HUD's skill-cooldown bar and "Skill Ready/Xs" label, the feet-level `skillReadyRing` ability pip, the fighter-detail panel's Skill ability row, key bindings (P1 `H`, P2 `;`, gamepad Y button) and their rebind-screen/controls-summary entries, bot AI's `skillChance`/skill-trigger logic in `BOT_DIFFICULTY`, and the skill wind-up sound-pitch case. One side effect worth flagging: Draven's Bulwark Stance was his *only* source of the shield/damage-reduction mechanic (`shieldFrames`), so removing it means Draven no longer has any damage-mitigation ability — his `shieldFrames`/`shieldRing`/`shieldReduction` infrastructure is still fully in place and still used by Seraphine's Astral Ward *special* (which independently grants a shield and was never a skill), just no longer reachable by Draven. Left his flavor text ("nearly unbreakable tank") as-is rather than rewriting character descriptions, which felt like scope beyond "remove skills."

**Passive HP regen ("healing over time") removed at the user's explicit request.** `cfg.regen` (a per-character passive-regen rate) and the `this.hp += this.regen * dt` tick that ran it every frame have both been deleted, along with the `regen:` field from all six `CHARACTERS` entries. This only ever restored a fraction of a percent of HP per frame passively — it did *not* touch the pickup heal (`PICKUP_HEAL_PCT`), Seraphine's Astral Ward special's one-shot heal-on-cast, or the now-removed Radiant Pulse skill (already gone from the skill removal above) — those are instant, on-cast/on-pickup heals, not "over time," and weren't asked to go.

**Projectiles passed straight through staircases.** Root cause: the projectile-collision check in `tickEffects()` only tested against `OBSTACLES` (pillars) and `PLATFORMS` (one-way floors, blocked only when the shot is below the platform's underside) — `TERRAIN` (steps/ramps) was never checked at all, so a low-flying shard/orb clipped straight through a stair's solid riser. Fixed by adding a third check: a projectile below a `step`-type terrain entry's height and within its `hw`/`hd` footprint is now blocked, same style as the existing platform check. Ramps are deliberately excluded — they're a smooth walkable incline with no vertical face to collide against, so "blocking" one would need slope-interpolated height math for a case that isn't really "a shot going through a wall" the way a stair riser is.

**Start screen (fighter-select menu) UI improved, on request.** The middle VS column had become a dumping ground for every menu-level setting added since Batch 9 (Rebind Keys, HUD Text scale, Audio Settings, stacked four-deep in a 110px column) — it competed with the actual P1-vs-P2 matchup for attention and made the "pick, pick, fight" flow harder to read at a glance. Changes: moved Rebind/HUD-scale/Audio into a new `.menu-footer` row (a muted, secondary-styled button strip below the whole select screen, visually separated by a top border) so the VS column only holds what's actually about the upcoming fight (VS label, status, bot difficulty). Each side panel's Bot-toggle/Random buttons moved from two stacked full-width buttons into one `.side-actions` row, saving vertical space. `#vs-status` gets a `.ready` state (bigger, cyan, gently pulsing via a CSS animation) toggled from `refreshMenuUI()` the instant both sides are confirmed, instead of the "Fight!" text just quietly changing color like every other status message. The `<h1>` title got a size/letter-spacing bump and a small gradient underline (`.brand-divider`) for a bit more visual presence instead of a single flat text-shadow line. Not visually verified in an actual browser — this is CSS/DOM structure only, checked for JS correctness (the `.ready` class toggle) via the usual syntax+mock-harness pass, not for how it actually looks.

**You could walk straight up any terrain, no matter how tall, without jumping — including onto Sundered Stair's tallest (54-unit) step from ground level.** Root cause: `groundLevelAt()` snaps a grounded fighter's `z` straight to whatever height is under their new feet every frame, with no limit on how big that jump in height could be — so sidestepping into the base of a tall step teleported you onto its top exactly the same way a gentle few-unit lip would. Fixed with a new `Fighter.resolveTallTerrain()`: while grounded, a move that would raise you more than `MAX_WALK_STEP_UP` (20 units) in one step now gets blocked like a wall instead of auto-climbed — tried as a full move, then X-only, then Y-only, then reverted entirely if none of those clear it (same axis-separated slide-along-the-wall approach `resolvePlatformWalls` already used for platforms). Sundered Stair's individual risers are 18 units each, under the cap, so climbing the actual staircase step-by-step is untouched — only skipping straight to a tall step from the side, or off the correct path, now requires an actual jump. Bot AI's "purposeful jump" check (Batch 6) is extended the same way, so bots don't stall at the base of terrain they now can't just walk up.

**Sundered Stair's staircase wasn't aligned with the (west) arena wall.** It sat with ~85 units of unexplained flat floor between the arena boundary and the base of the first step, reading as floating/misplaced rather than built into the level. Repositioned so the first step's near edge sits flush on `ARENA_LEFT`. Folded into the broader map-rescale pass below.

**Maps made bigger, on request, plus more maps and more/taller terrain.** The virtual coordinate space (`VIRTUAL_W`/`VIRTUAL_H`) grew from 900x500 to 1170x650 (a uniform 1.3x) — every hardcoded pixel position that assumed the old space (canvas attributes, `#game-container`'s CSS `aspect-ratio`, the P2 HUD panel's x-offset, camera position/framing distances, the directional light's shadow-camera frustum, fog near/far) was updated to match; arena-bounds-derived values (`ARENA_LEFT/RIGHT/TOP/BOTTOM`, `ARENA_CX/CY`, the floor plane, rim-edge trim, `PICKUP_SPOTS`, hazard placement) needed no changes since they were already computed from `VIRTUAL_W`/`VIRTUAL_H` rather than hardcoded. All four existing maps got a uniform 1.3x rescale of every horizontal coordinate (position/footprint) — **heights were deliberately left unscaled**, since vertical reach is governed by `JUMP_VZ`/`GRAVITY` (unchanged), not by how wide the map is; scaling both would have thrown off which platforms are jumpable. Two brand-new maps were added (**Skyreach Spire**: a three-tier platform staircase climbing to a height-200 "throne" that's flatly unreachable in a single jump from the ground — has to be climbed tier by tier, with the last gap deliberately tight for the slowest character; **The Shattered Bridge**: two ground shores connected only by a broken chain of floating stepping-stones, the center one sitting right at the edge of single-jump reach). Every existing map also picked up at least one new terrain/platform piece it didn't have before (shallow rises on Astral Proving Grounds, which previously had zero terrain; a central step on Twin Ramparts; a hard-to-reach side platform on The Colosseum Ring; Sundered Stair's fixed staircase gained a fourth tier plus a two-platform chain leading to a genuinely hard-to-reach height-160 platform, unreachable except by climbing the stair first). All six maps' spawn points and geometry (arena-bounds containment, obstacle/platform/pillar overlaps) were verified with a standalone script exercising the game's own `assertSpawnsClear()` plus additional overlap checks — not visually confirmed in a browser, since none is available here.

**Jumping had no cooldown at all — you could jump again the instant you landed.** Added `Fighter.jumpCooldown` (new `JUMP_COOLDOWN = 60` constant — noticeably longer than a jump's own ~43-frame airtime, so landing doesn't mean you can immediately jump again), ticked down alongside the existing `attackCooldown`/`dodgeCooldown` pattern and gating the jump trigger the same way. Surfaced in the `?debug=1` per-fighter state readout (`jumpCD:`) next to the existing `dodgeCD:`.

**Characters rebuilt as actual humanoid figures, on request, with attack/special animations reworked to match.** Every character used to be an abstract shape (a box/octahedron/sphere "body") with a weapon prop bolted on and animated in isolation (the prop rotating/thrusting/pulsing on its own, unconnected to any body part). New shared `buildHumanoidBase(color, opts)` builds an actual person-shaped rig — two legs, a torso, a head, and two shoulder-pivoted arms each ending in a hand socket — reused by all six character builders, which now attach their weapon(s) to a hand instead of floating them in space. `animateWeapon()` was rewritten from three prop-level animation types (rotate/thrust/pulse) down to two rig-level ones: **'swing'** rotates one arm's shoulder pivot (or an array of pivots — Voss's twin daggers stab together, Draven's two-handed hammer grip swings both shoulders in sync) through a wind-up-then-strike arc, so an attack now reads as an arm actually swinging a held weapon; **'cast'** raises the casting arm and holds it through the whole active window (rather than swinging back down mid-cast like a melee follow-through would) while flaring the held prop's scale, for the two ranged casters. Lyra keeps her ambient orbiting shard (attached to the main body, not a hand, so it doesn't fight the new arm-swing transform) alongside a second, smaller shard actually held in her casting hand; Seraphine keeps her halo the same way. Draven's old shoulder-armor pad detail was dropped rather than reworked to fit the new rig, given the scope already involved. Verified with `node --check` and the mock-DOM runtime harness (both clean); not visually confirmed in a browser, since none is available here — proportions, weapon-hand placement, and swing angles are a reasoned first pass, not a rendered/previewed result.

**Tutorial ("How to Play") added, on request.** New `#tutorial-screen` overlay, styled to match the game's existing card/panel visual language (dark slate panels, cyan accents) rather than a plain wall of text — a responsive card grid (`.tutorial-grid`, auto-fits down to one column on narrow widths) covering Objective, Movement & Jumping (including the new jump cooldown), Basic vs. Special (including how meter actually builds), Dodge, Hazards & Pickups, and a Controls card. A prominent bordered "How to Play" button sits right under the title (separate from the muted settings-button footer, since this is the one thing a brand-new player most wants), and it auto-opens the first time the game loads in a browser — and every load after that — until the "don't show automatically" checkbox is checked, persisted via the same `safeLSGet`/`safeLSSet` helpers as the other settings. Verified with `node --check`, the mock-DOM harness, and a manual `<div>` open/close tag-balance check across the markup; not visually confirmed in a browser. **STANDING RULE going forward (user asked to remember):** every mechanic change must also update this tutorial's cards so it never drifts out of sync.

**Damage multiplied 5x, on explicit request.** Every character's basic-attack `dmg` and every special's hardcoded damage number were multiplied by 5 (Kaelen 7→35, Lyra 6→30, Gorgonok 10→50, Voss 5→25, Draven 14→70, Seraphine 5→25; specials scaled to match, e.g. Draven's Ground Breaker 45→225). Deliberately makes time-to-kill much shorter — works with the arena-collapse mechanic to force decisive fights. `STAT_MAX.dmg` (the select-screen stat-bar normalizer) was bumped so the bars still read sensibly.

**Round timer removed and replaced with Arena Collapse, on request.** There's no clock counting down to a timeout draw anymore — the whole timeout branch (`decideRoundResult(byTimeout)`, the `roundTimeLeft <= 0` path, `ROUND_TIME`/`roundTimeLeft`) is gone. Instead: new constants `SHRINK_INTERVAL`/`SHRINK_STEP`/`CRUSH_GAP`/`CRUSH_DPS` and state `shrinkTimer`/`shrinkAmount`/`playLeft`/`playRight`/`crushing`. Every `SHRINK_INTERVAL` seconds `updateArenaShrink()` pulls the playable left/right bounds inward by `SHRINK_STEP`; `clampToArena()` now reads `playLeft`/`playRight` (the shrinking bounds) instead of the fixed `ARENA_LEFT`/`RIGHT`, so fighters are physically squeezed toward center. Two glowing red wall-slab meshes (`shrinkWallLeftMesh`/`shrinkWallRightMesh`, `syncShrinkWalls()`) visualize the closing bounds. Once the gap hits `CRUSH_GAP`, the walls snap shut (`crushing = true`), input/combat freeze, and both fighters lose a **flat, equal, max/current-HP-independent** `CRUSH_DPS` per second (`hp -= CRUSH_DPS * dt/60`) until one dies — reusing the existing `hp<=0 → DEATH` flow so "whoever dies first loses" falls out of logic that already existed. `render3D` squeezes each body flat along X while crushing. The HUD's timer readout became "Walls close in Ns" / "CRUSHING!". State reset in `startRound()`. `decideRoundResult()` simplified to no longer take a `byTimeout` arg.

**Aim-lock removed, on request.** The modifier that let you move one way while facing another (`aimlock` binding, the `aimLock` local in `update()`, the `if (!aimLock) setFacing(...)` guard) is fully gone from bindings, both input branches, the controls summary, and the rebind action labels. Movement always sets facing now.

**Verification caught a real balance bug: a landed special instantly refilled its own meter.** Found while writing a combat-verification script (see below) that actually calls `doBasicAttack`/`doSpecial` against a live opponent instead of only checking that the mesh/animation code doesn't throw. Root cause: `takeDamage()`'s "attacker builds meter from damage dealt" logic (the Batch 4 comeback mechanic) applied to *all* damage sources, including a special's own hit — and specials deal enough damage (175-225, after the 5x pass) that `amount * METER_DEALT_RATE * meterRateMult` clamps straight back to 100 the same frame the meter was spent, for any special that connects via an omnidirectional AOE check (`distBetween`) or a melee cone that happens to be facing the target. This existed in a smaller form before the 5x damage change (a ~76% partial refill) but the 5x pass turned it into a full, instant, always-on refill — specials could chain back-to-back forever once the first one landed. Fixed by gating the attacker's own meter gain on `attacker.atkKind !== 'special'` — a special's damage still lands and still builds meter for the *defender* (the taken-damage comeback mechanic is untouched), it just no longer pays for its own recast; only basic-attack damage (plus the passive trickle) rebuilds a spent special bar now.

**New verification tooling: a live combat-exercise script**, added alongside the existing mesh/animation-only check, because that check couldn't have caught the bug above (it never calls `takeDamage`). `combatcheck.js` constructs a real `Fighter` pair per character, calls `doBasicAttack()` (confirming a melee effect or projectile is produced) and `doSpecial()` with the meter and `atkKind` set to match how `updateActionState()` actually invokes it in-game (confirming the meter is consumed), for all 10 characters. All 10 pass. This directly exercises the brief's own "every character's attack/special fires, connects, shows an effect" verification item, which no prior tooling in this file actually tested end-to-end.

**Bot AI's ranged-vs-melee detection missed the new `bolt` attack type**, found by the same pass — Aurelia (added this session, `atkType: 'bolt'`) would have played like a melee bot (walking into range, never kiting) instead of a ranged one, since `botDecide()`'s `isRanged` check only listed `'shard'`/`'orb'`. Added `'bolt'` to the check.

Fixed by switching `#ui-overlay` to `justify-content: flex-start` with `overflow-y: auto` — top-aligned and scrollable, so a taller-than-viewport select screen is fully reachable by scrolling instead of silently clipped at both edges. Removed the now-redundant nested scroll on `.select-row` (a scroll region inside a scroll region just fights the mouse wheel).

Pure CSS, no layout structure changes.

**Arena Collapse reworked to close on all four sides + map edges "fall away" instead of red walls, on request.** Three changes to the collapse mechanic: (1) It now shrinks **X and Y proportionally** (all four bounds pull toward center by the same fraction each tick, keeping the arena's shape) instead of only left/right. New `shrinkFrac`/`shrinkTargetFrac` (a 0→1 collapse fraction, smoothly eased toward a stepped target so the walls read as continuously closing) drive `arenaBoundsFromFrac()`, which sets `playLeft/Right/Top/Bottom`; `clampToArena()` now uses all four. (2) The old glowing red wall slabs are **gone** — instead the floor plane shrinks to the current bounds and any map geometry (pillars/steps/ramps/platforms) now outside them **drops straight down into the void and vanishes** ("as if it never existed"). Required making every map-builder (`buildPillarMesh`/`buildStepMesh`/`buildRampMesh`/`buildPlatformMesh`/`addRimEdge`/`addCornerGlow`) return its group and building them positioned via a group origin (not baking `worldX/worldZ` into child positions) so each can be dropped as a unit; `loadMap()` tracks them in `mapEdgeObjects` (tagged with game x/y) + `borderDecor` (rim/corner decor, hidden the instant collapse starts); new `syncArenaCollapse(dt)` scales the floor and culls out-of-bounds objects. (3) On the final shut it stays fully visible (no obscuring props) and each fighter is **crushed in place on their own side** — `render3D`'s crush squish now flattens the footprint in both X and Z while popping up in Y (a can-being-stepped-on look) rather than only flattening X. Verified with a standalone `collapsecheck.js` that simulates 120s: confirms both axes shrink to center, crush triggers (~54s of a fully-stalled fight), and all edge objects fall away.

**Bug fixed: standing on a tall platform "teleported" you off it.** Root cause: the platform-landing check in `update()` required `!this.grounded && this.z >= p.height`. The instant you landed (grounded = true), the next frame's gravity dipped your z a hair below `p.height`, so *neither* condition held, the platform stopped counting as ground, and you fell straight to the floor. Fixed by replacing that with a "descending onto the surface" test using a small `SURFACE_EPS` (5 units): you count as standing while within a few units of the surface (absorbing the per-frame gravity dip), while a fighter at ground level far below a tall platform still can't qualify — preserving the one-way "must jump up to it" behavior without the fall-off. Verified with `platformcheck.js` (fighter stays at z=130 on a height-130 platform for 180 frames, never dips).

**Bots massively improved at ranged shooters + new 'insane' difficulty, on request.** The core ranged-bot bug: `update()` always set facing from *movement* direction, so a kiting ranged bot (moving away from its target) faced backward and fired its projectiles away from the opponent — they were nearly useless. Fixed by giving bots an internal aim override (`botFaceX/botFaceY`, the bot-only equivalent of the removed player aim-lock) that `update()` applies *after* movement, so a bot always faces — and shoots at — its target regardless of which way it's moving. Ranged bots additionally **lead** the target (aim where a speed-7 projectile will intercept it, using the opponent's velocity), so shots connect against a moving target; verified with `rangedbotcheck.js` (13 shots toward a weaving opponent, 0 away — previously all away). Difficulty tiers gained `lead`/`strafe`/`relentless` flags: higher tiers strafe perpendicular to be harder to hit and passively slip shots, and don't waste airtime on idle jump-twitches. **Bug fixed (second cause of the blank character-select): `getWallTexture` fed an `undefined` color to `addColorStop`.** After the Layers polyfill, the menu was *still* blank — the DevTools console showed `Uncaught SyntaxError: Failed to execute 'addColorStop' on 'CanvasGradient': The value provided ('undefined') could not be parsed as a color` at `getWallTexture → buildOuterWall → loadMap` (the top-level `loadMap(MAPS[...])`), again dying before `buildGrid()`. **Batch 15 — Double Jump upgrade + every high platform made reachable.** The purchasable (1000-coin, account-wide) air jump, plus the map retuning it exists to justify.
- *Mechanic:* `Fighter.usedDoubleJump`, one air jump per airborne stretch, re-armed on any landing (ground, step, or platform). **Reset-style** (`vz` is set back to `JUMP_VZ`, not added to the current `vz`) — the standard, better-behaved form, and it gives a bounded ceiling instead of an additive one that could be stacked at liftoff to trivialize everything. A small ring puff fires on use so the air jump reads as deliberate rather than as a physics glitch.
- **The non-obvious bug this had to avoid.** The ground jump reads a *held* key (`keys[b.jump]`), which is fine because `grounded` is what stops it re-triggering. A mid-air second jump can't work that way: the same physical press that started jump 1 is almost always still down on the very next frame, so a held-state check would auto-spend the air jump one frame after takeoff with no second press from the player at all. Fixed by tracking a genuine key-**down edge** for the air jump only (`consumePress(b.jump)`; nothing else consumes the jump key's press, and the gamepad's `gp.jump` was already edge-triggered), leaving the ground jump's held-state check untouched so existing jump feel is bit-for-bit unchanged. This is verified directly: holding the key peaks at a single jump's height (~92 gain), not a double's (~167).
- *Scope cut:* human input only. Bots don't need it (their pathing never routes through these perches) and giving them a movement option the AI wasn't written around risks worse behavior, not better — asserted in the checker that a bot never sets `usedDoubleJump`.
- **Every "unreachable" high platform is now genuinely reachable, which was the actual request.** Measured the best-case air jump against a real `Fighter` by sweeping the second-press frame: **~184 units of gain, peaking when the press lands on the first jump's apex frame** (21). Then audited every map's tall blocks against that. Four wall-tops (Twin Ramparts 285, Molten Foundry 270, Overgrown Sanctuary 250, The Colosseum Ring 250) sat at gaps of 188-215 — flatly unreachable even with the upgrade — and a fifth (The Shattered Bridge 270, gap 175) was reachable only with a frame-perfect apex press, which isn't "reachable" in any sense a player would recognize. All five pairs were lowered so every gap is **160-163**, leaving a wide timing window rather than demanding a pixel-perfect input. Each is still 222-255 units tall against a 46-unit eye height, so their actual job — blocking sight lines as interior lane dividers — is completely unchanged; only their tops became attainable. (These are thin 26-30-half-width dividers, so the reward is a narrow high perch, which pairs naturally with the look-up/down aiming in Batch 20.)
- *Checker improvement worth noting:* `reachabilitycheck.js` now classifies a platform as wall-vs-perch by **footprint thinness** (`min(hw,hd) <= 32`) rather than by height. Height gets re-tuned — this batch changed five of them — so a height threshold would have silently reclassified a wall as a perch the moment it was adjusted, and quietly stopped checking the thing it was written to check. It runs two passes: ordinary perches must be reachable *unaided*, and **every** platform including wall-tops must be reachable *with* Double Jump. Both pass for all ten maps.
- Verified with `doublejumpcheck.js` (16 assertions, all passing — including the held-key trap, one-air-jump-only, re-arm-after-landing, no-op before purchase, bots never using it, and the best-case-timing sweep clearing the retuned gaps) plus the reachability audit and the existing progression/cheat/desktop/touch suites, all green, zero console errors. **Batch 20 — Camera pitch (look up/down) + pitched projectile aiming.** Done out of numeric order, immediately after Batch 15, because it's the other half of the same problem: Batch 15 made the tall perches *reachable*, and this makes them *fightable* — before it, someone on a high platform couldn't be shot at all, since projectiles only ever flew dead level.
- *State:* `Fighter.pitch` (radians, positive = up) + `lookBy(radians)`, clamped to ±42° — enough to sight the tallest perch from the floor and to shoot down from one, without letting the view roll past the horizon. Deliberately kept **separate from `fx`/`fy`**, which stay a purely horizontal facing vector, so every existing 2D movement / melee-cone / bot-steering calculation is untouched.
- *Input, following the established binding pattern rather than a bespoke path:* new `lookUp`/`lookDown` entries in `DEFAULT_BINDINGS` (**P1 R/V**, **P2 `;`/`'`** — free keys beside each side's existing cluster), which automatically flow into the rebind screen (now 20 rows) and `controlsSummary()`. Gamepad uses the **right stick's Y axis** (`axes[3]`) — an axis, not a button, since all four face buttons are already spoken for and analog pitch is what you actually want; a pad reporting fewer axes yields 0, i.e. exactly the pre-batch behavior. Touch gets a **drag-to-look zone** in the upper part of each side's pad area, mirroring the existing `touchTurn` analog pattern with a new `touchLook`; it returns to level on release, since a sticky pitch with no visible cause reads as a broken camera.
- *Camera:* `positionFpsCamera`'s look-target height, previously a hardcoded `-4` (or `-22` during the intro drop), is now `-4 + tan(pitch) * LOOK_DIST`. The intro drop keeps its own hardcoded steep tilt — it's a cinematic, not something the player aims through.
- *Projectiles inherit the shooter's aim,* which is the part that actually matters for gameplay: a new `projectileVelocity(speed, fx, fy, pitch)` splits speed into horizontal (`cos`) and vertical (`sin`) components, so a pitched shot is **redirected, not sped up** — total velocity is preserved, keeping range and travel-time feel identical. Straight-line, no gravity, as intended. Both spawn sites (the basic `fireProjectile` and Lyra's volley fan) use it, and the travel loop gained one line (`if (p.vz) p.z += p.vz * dt`). `verticalHit` needed **zero** changes — it was already written against an arbitrary `p.z`.
- *Also needed, and easy to have missed:* vertical despawn bounds. A downward shot would previously have sunk through the floor forever and an upward one climbed forever, both leaking meshes, because the existing despawn only tested horizontal arena bounds — a shot going straight up never crosses them. Downward shots now bury into the surface under them (with a small dust ring so it reads as an impact rather than a vanish) and upward shots die at a `PROJECTILE_CEILING`.
- **Regression safety, asserted rather than assumed:** at pitch 0, `projectileVelocity` returns exactly `(fx*speed, fy*speed, 0)` and the travel loop's `if (p.vz)` guard skips entirely — so every bot-fired shot (bots never set `pitch`) is bit-for-bit what it was before this batch, and the bot's existing projectile-lead math stays correct with no changes.
- **A real regression this batch introduced and the tests caught.** The new touch look-zone initially spanned the top 55% of each side with `pointer-events: auto`, and as a later DOM sibling it painted over `#touch-pause-btn` and swallowed its taps — the mobile pause button silently stopped working. Caught because the pause suite started reporting *inverted* results (tap didn't pause; the subsequent Resume click paused instead), consistently across three runs rather than flakily, which is what distinguished a real bug from the timing race that had produced a similar-looking failure earlier. Fixed by starting the zone below the button's row and giving the button a higher `z-index`. Also hardened the pause checker to `waitForFunction(gameState === 'FIGHT')` instead of a fixed sleep, since `togglePause()` deliberately no-ops outside FIGHT/DEATH/ROUND_END and tapping too early looked identical to a real failure.
- Verified with `pitchcheck.js` (27 assertions) and `touchlookcheck.js` (7). The headline pair: a **level** shot provably *cannot* hit a target 150 units up (the exact limitation this batch removes), while a shot **aimed** at it — pitch computed from the real geometry, `atan(Δheight / distance)` ≈ 20° — connects; likewise a 37°-downward shot from a height-200 perch hits someone on the floor. Plus clamping, proportional (non-snapped) look, speed preservation, camera rotation responding in both directions, despawn bounds, binding/rebind/controls-summary wiring, live keyboard drive through the real `update()` loop, and the bot-unchanged regression. All prior suites (progression, cheat/sandbox, double jump, reachability, desktop, touch, pause) still green, zero console errors. Tutorial's First-Person View card updated per the standing tutorial-sync rule.

**Batch 21 — Progression split per player; bot mode moved into the sandbox (both on request).** Two corrections to Batches 12-14, which had built a single shared account and had the bot rule backwards.
- *Per-player progression.* `astralClashProgression` is now `{p1: {...}, p2: {...}}`, and **every** accessor/mutator takes a side as its first argument (`isCharUnlocked(side, name)`, `upgradeLevel(side, name, trait)`, `buyUnlock(side, name)`, `addCoins(side, n)`, …) — there is deliberately no longer any such thing as "the" progression, so a call site that forgets whose account it means fails loudly rather than silently spending the wrong player's coins. `Fighter` reads its own side's upgrades (via `isPlayerOne`), which means a **mirror match now correctly gives the two Kaelens different stats** if their owners have bought different upgrades. Each side panel shows its own purse plus a shortcut into its own Shop tab; the Shop itself gained Player 1 / Player 2 tabs rather than being duplicated. Grids lock independently, so the two rosters can legitimately differ.
- *Migration, not a reset.* A Batch-12-era save (single blob with `coins` at the top level) is detected and copied to **both** sides. Splitting the format shouldn't cost anyone progress they already earned, and picking one player to inherit it would have been arbitrary.

Correspondingly, `addCoins` is a **hard no-op while the sandbox is on** — since the override deliberately never writes to the real save, letting it *pay into* that save would have turned the sandbox into a farming shortcut for the very progression it bypasses. Turning the sandbox off also clears any bot side that was enabled inside it, so a bot match can't leak into progression play.
- **A TDZ bug caught immediately by the checkers** — the fourth time this file has hit this exact class. `shopSide` was declared with `let` next to `buildShop()` far down the file, but `refreshCoinDisplays()` reads it and runs during initial load, so the whole script died on `Cannot access 'shopSide' before initialization` and `window.ACDebug` never appeared. Each now enables the sandbox first, which is genuinely what a human wanting a bot match has to do too.
- Verified with `progressioncheck.js`, now **45 assertions**, including a dedicated per-player-isolation block: P1's coins/unlocks/upgrades/Double Jump provably do not leak to P2, P2 cannot spend P1's coins, each grid shows its own lock count, the mirror-match stat divergence holds, the winner is paid more than the loser into the correct purse, the sandbox banks nothing and leaves both purses intact, and a legacy shared save migrates to both sides. `cheatcheck.js` updated for the inverted rule (bot toggle enabled *in* the sandbox, disabled outside it, un-clickable outside it, and cleared on sandbox-off). **Batch 19 — Game-mode select + Zone Control + Time Attack.** Done before the co-op batches because these two are still pure P1-vs-P2 (no third combatant), so they're far lower risk — and they build the mode plumbing the co-op modes will plug into.
- *`matchMode` is deliberately orthogonal to `gameState`.* `gameState` says where we are in the round lifecycle; `matchMode` says what winning means. It defaults to `'classic'`, and every mode-specific branch is an explicit check against it, so Classic's behavior is unchanged byte-for-byte and a mode that doesn't care about a system never appears in it. A new `#modeselect-screen` modal follows the `mapselect` precedent (opened mid-flow, closes back to what was underneath) rather than adding a top-level screen, reached from a button under the branding — **not** a gate in front of fighter-select, since `'classic'` is already a valid choice; same flag-don't-block stance as the existing mirror-match note.
- *Both new modes are single continuous matches with respawns,* deliberately skipping the best-of-3/pip machinery instead of trying to nest "best of 3 first-to-3-KOs" — that composition was never asked for and would have meant resetting score mid-match and syncing it against collapse timers for no benefit. New `Fighter.respawn(spawn)` is the shared primitive: full HP at spawn, brief i-frames so you can't be spawn-camped, and an **explicit clear of everything that could otherwise carry across a death** (hitstun, root, burn DoT, shield, in-flight action state, queued follow-ups, live projectiles) — leaving any of those attached to a "fresh" fighter is exactly what produces someone who respawns already staggered or on fire. The KO animation still plays in full; only what follows it changes.
- *Zone Control:* a ground ring at arena centre; standing in it **alone** banks control time, contested or empty banks nothing — the simplest rule that keeps "knock them out of the ring" as the core play. Containment is a flat 2D test that **ignores height, on purpose**: several maps have a platform essentially at arena centre, so a floor-only test would have made the zone unreachable there; ignoring z means standing on that platform also contests the ring, which is free verticality rather than a bug. The ring tints and pulses to whoever holds it, so control is readable from inside the fight and not only on the HUD. Arena Collapse converges on the same centre point, so the closing walls squeeze both fighters toward the contested spot instead of fighting the mode.
- *Time Attack:* fixed at **3** KOs — not player-configurable, per the request. 3 echoes the existing best-of-3 motif and, at this game's real time-to-kill, lands a match around 1-3 minutes, matching the pacing everything else is tuned to.
- *Collapse reused as the safety valve for both.* If a continuous match somehow stalls until the walls slam shut, it resolves on that mode's own score (held seconds / KO count, tie = draw) rather than grinding both fighters down — which, with respawns, would never actually resolve. The game-over title reports each mode's own score rather than round pips it never used, and coin payouts route through per-mode keys (same numbers today, but separable).
- **A layout bug caught by looking at the screenshot, not by the assertions.** The first pass drew the mode readouts at the round-pip row (y≈56). The per-player HP panels occupy y 46-108 out to 420px wide, and in split-screen this shared block is re-drawn *centred in each half* — so a wide centred readout lands straight on top of a panel, which it did. Moved both mode readouts below the panels (y≥120); the Zone bars now grow from the outside inward so "who's closer to winning" reads as two bars racing toward the contested centre.
- **Two more TDZ errors, same family as every prior one,** both caught immediately because `window.ACDebug` failed to appear: `shopSide` (Batch 21) and then `MATCH_MODES` were declared with `let`/`const` down beside the code that uses them most, but menu code runs during load and reads both. Fixed by moving both declarations up with the other early state, each with a comment naming the trap. That's now four instances of this exact bug in this file's history — the pattern is unambiguous: **anything the load-time menu build touches must be declared before it, regardless of where it thematically belongs.**
- Verified with `modescheck.js` (**36 assertions**), which drives real matches through the actual game loop rather than poking state: the picker lists three modes with exactly one active and relabels its button; in Zone Control the ring builds, occupancy is detected, a sole occupant banks time while the other doesn't, a contested ring banks nothing for anyone, reaching the target ends the match with the leader as winner, and the ring is disposed at match end; in Time Attack a KO credits the killer and **continues** the match with the victim respawned at full HP at their spawn with i-frames and no stale hitstun/burn/projectiles, and the deciding KO ends it; and — the regression guard that matters most — **Classic is unaffected**: not continuous, no ring, and a KO still advances the round rather than respawning. All prior suites green, zero console errors. Tutorial gained a Game Modes card per the standing tutorial-sync rule.

**Batch 16 — Co-op third-combatant infrastructure.** The structurally riskiest change in this whole arc, deliberately landed last on a codebase that was green everywhere else. `player1`/`player2` were hardcoded as exactly-two throughout, so a co-op boss needed real seams rather than an extra variable.
- **The hard part wasn't the win check — it was target resolution.** Combat is single-opponent-shaped much deeper than it looks: `update()` passes one `opponent` into `tryStartAction()`, which **stores** it on the fighter (`atkOpponent`) at the moment startup begins, and `doBasicAttack`/`doSpecial` resolve against that stored reference much later; `tickEffects()` likewise tests in-flight projectiles against exactly that one opponent. A fighter was therefore structurally incapable of hitting anyone but "the other player." Two helpers are the seam: `pickTarget(attacker, defaultOpponent)` (a player aims at the boss; the boss aims at the nearer *live* player) and `getExtraCombatTargets(fighter)` (extra bodies a projectile should also be tested against). **Both are pure pass-throughs outside co-op** — `pickTarget` returns its argument and `getExtraCombatTargets` returns a shared empty array — so classic/zone/timeattack are byte-for-byte unchanged, which is asserted rather than assumed. Resolved **once** at the top of `update()` into a local rather than at each of the ~9 action call sites, so there's a single place this can be wrong.
  - *One subtlety worth recording:* the first version of the projectile pass added an is-alive guard to the primary target too. That would have quietly changed classic behavior — a shot can currently still land on a fighter who already hit 0 HP during the death sequence, which `endMatch`'s "use the winner decided at KO time, don't re-derive from current hp" comment explicitly depends on. The primary opponent is now tested with *exactly* the original predicate; only the co-op extras get the liveness guard.
- *Rendering:* a new `LAYER_BOSS_BODY` that **both** player cameras enable unconditionally. It costs nothing outside co-op (nothing is on that layer), and it means the boss is visible to both players without either being able to see through it. The two P1-vs-P2 readability tweaks (P2's darkened materials, P2's ground ring) are explicitly skipped for a boss, which is neither side.
- *The boss reuses `Fighter` wholesale* — same `update()` pipeline, so it inherits movement, gravity, hitstun, the action state machine and every animation for free — with `isBossEntity` set as a plain post-construction property and its config read from a separate **`BOSS_MAP`**. Keeping it out of `CHARACTERS` is load-bearing, not tidiness: `buildGrid` iterates `CHARACTERS` unconditionally, so anything in there becomes a pickable fighter on the select screen. Player upgrade multipliers are skipped for a boss (already guarded in Batch 12), so boss/wave scaling is the only multiplier in play and the two systems can't double-dip. Deliberately **not** fed through `resolvePlayerCollision`: a much larger body shoving players around adds feel risk for no requested benefit, so it overlaps rather than pushes.
- *PvE gets its own result path* (`endCoopMatch`), because `endRound`/`endMatch`'s `roundWins`/pips/"player1 beat player2" are all *versus* concepts — reusing them would have printed "Kaelen (Player 1) Wins" about your own teammate. One attempt, one outcome: "Victory!"/"Defeat", a PvE summary, and a **team** coin payout (same to both players, since both fought the same fight). The menu framing follows: the VS badge becomes **TEAM** and the mirror-match note is suppressed, since neither means anything between allies.
- *Deliberate scope cut, flagged not half-built:* if **either** player goes down, the run ends. Real down-but-revivable co-op needs a player-facing sub-state (spectating, revive timers, a revive interaction) that doesn't exist anywhere in this file — a bigger feature than the boss itself.
- **A design bug caught by looking at the screenshot, not by any assertion:** Arena Collapse was still running in co-op, and the crush would have killed the team at ~56s — long before two players could work through a 3000+ HP boss, making the mode unwinnable by construction (and guaranteeing a loss on an open-ended Survival run). Collapse is now disabled in co-op: the boss *is* the pressure there. Its HUD block is skipped too, since the boss bar is the only progress readout PvE needs.
- *Two test-methodology fixes worth recording,* both cases of the harness being wrong rather than the code: (1) pinning fixed coordinates before a frame isn't enough to hold a fight in place — the simulation moves everyone *after* the assignment, and the boss's AI circled behind P1, putting itself outside the swing cone; the check now re-places and re-aims P1 at the boss's **live** position each frame, so it tests hit resolution rather than whether P1 can chase. (2) A first attempt polled for `FIGHT` while already *in* `FIGHT`, exiting before the KO it was waiting for — the mode checks now wait for `DEATH` first.
- Verified with `coopcheck.js` (**30 assertions**) driving real matches: the boss spawns on its own layer, both cameras see it, it has a boss-sized HP pool, and it is **not** in the pickable roster; a player's attack lands on the boss and **not** on their teammate (friendly fire off); the boss damages a player and re-targets to whoever is nearer; killing it ends the run as Victory with no versus framing, and either player falling ends it as Defeat; a cleared Survival wave advances the counter and spawns a tougher challenger **without** ending the run; and — the guard that matters most — **PvP is untouched**: not co-op, no boss entity, and a KO still runs the versus death/round path. All eight other suites still green, zero console errors.

**Batch 17 — Karrigos, the Hollow Titan.** The purpose-built co-op boss, replacing Batch 16's scaled-roster stand-in.
- *Built on the existing rig, not new geometry.* `buildKarrigosMesh` uses the same `buildHumanoidBase` every roster character uses, at 1.5x scale with heavy proportions (broad torso, thick limbs, small head) — so it inherits the shoulder pivots, hand sockets and every animation hook for free, and only the silhouette and materials are new work. A golem is also thematically off-roster (none of the ten are giants), so it reads as a boss without a new art pipeline. Stone fists are built inline rather than via `buildFistProp`, which bolts on bright gold emissive knuckles that are right for Ignis' burning gauntlets and wrong for rock.

**Batch 18 — Survival Waves pacing and polish.** Batch 16 made waves *work*; this made them feel like a run.

Now the field clears, a `WAVE_BREAK_FRAMES` (~2.5s) countdown runs, and the next challenger arrives when it elapses. Ticked in `stepFight` rather than in `onBossDefeated` so it counts real frames.
- *Challengers arrive from the far corner.* `farthestSpawnFromPlayers()` picks whichever of the arena's four inset corners has the greatest distance to its nearest live player. Corners rather than the map's own spawn points, so it works identically on all ten maps with no per-map wave data. Spawning an enemy in someone's face is the cheapest possible source of unavoidable damage and reads as unfair rather than as difficulty.

A co-op boss's mesh therefore stayed in the scene behind the select screen and into the next match. Now both routes dispose. The consequence is that Survival is a "one health bar, how far can you get" run rather than an endless grind, which is a legitimate survival design but does cap run length by your starting HP. **If longer runs are wanted, a small per-wave heal is the single knob** — flagged here as the intended lever rather than changed unilaterally.
- *Two test-methodology findings, both about measuring rather than about the game:* (1) The checkers were timing out on waits that looked generous — headless software rendering (swiftshader) runs this page at only **~3-4 fps**, so a 150-*frame* breather takes over ten real seconds. Anything measured in game-frames needs a far larger wall-clock budget than the frame count suggests; the budgets are now sized for that and the reason is commented. (2) "Later waves are tougher" failed intermittently on raw HP, correctly: each wave is a *random* roster character and their base HP spans 320-520, so wave N+1's absolute HP can legitimately land below wave N's. ## Batch 23 - Survival becomes squads, and the tests move into the repo

Survival was one strong enemy at a time; it's now a squad of purpose-built weaklings, with a real boss every fifth wave.

- *Generalized the single co-op enemy slot into a list* (`coopEnemies`). Batch 16 deliberately deferred arbitrary-N because one slot was all the boss fight needed; multi-enemy waves make it mandatory. `pickTarget` now aims at the **nearest** live enemy, a player's shot can hit **any** live enemy, and a wave clears only when every member is down. All three are pure pass-throughs outside co-op, so PvP is byte-for-byte untouched.
- *Three Survival-only enemies rather than reskinned roster fighters* (Grint 130hp/speed 4.4, Slagling 150hp ranged, Hollowkin 260hp tank). A wave of "Thornes" reads as a mirror match gone wrong; and because these are only ever AI-controlled they can be lopsided in ways a player-pickable character couldn't fairly be. They live in `BOSS_MAP` for the same load-bearing reason as Karrigos: **anything in `CHARACTERS` becomes a pickable fighter on the select screen.**
- *Wave composition:* 2 enemies growing to a cap of 5, drawn **without replacement** from a shuffled pool. Independent per-slot rolls produced "two Hollowkin" - the same silhouette twice, and a wave of two tanks is far harder than two skitterers, so same-numbered waves swung wildly in difficulty. Every 5th wave is a Karrigos boss wave instead of a squad.

**The tests are now committed, under `tests/`.** They previously lived in a scratch directory, and that directory was wiped mid-project, taking all ten checker scripts with it. ## Batches 25-29 - The art overhaul

The brief: characters should have faces and read as human/robot/animal rather than differing only by colour, the arenas should look refined and be *fair*, the crush should be a real cinematic, and the whole thing should look like a commercial shooter instead of clay.

### The pipeline (Batch 25)

- *Characters are Blender-authored now, not primitives.* Kaelen is a 23,332-triangle humanoid with full PBR (base colour + metallic-roughness + normal), a 19-joint skeleton, and six skeletal clips: Idle, Walk, Run, Jump, Hit, Death. The game had **no walk cycle at all** - characters slid with rigid legs - so locomotion is the single biggest contributor to it reading as finished.
- *Additive by construction.* `initMesh` prefers `buildRiggedCharacter(name)` and falls back to `PROC_MESH_BUILDERS[name]`. Both produce the same `userData` contract, so `animateWeapon`, the hit flash and the death fade need no branching, the roster converts one character at a time, and the game is never in a broken half-state.
- *Locomotion on an AnimationMixer, attacks still procedural.* The mixer updates BEFORE `animateWeapon` so the tuned per-character attack swing wins on the arms it drives. That layering is what let baked walk/run coexist with all thirteen existing `weaponAnim` types instead of replacing them. `_applyArms` gained an `axis`: a procedural arm is a Group swung about Z, a skeleton's bone about local X with the opposite sign.
- *Weapons are transplanted off the procedural build* rather than re-declared beside the rig, so there is no second copy of each character's weapon and swing timings to drift.
- **Measured, not assumed.** Bone positions come from slicing the mesh in Z and clustering vertices by X to find the real shoulder/elbow/wrist/hip/knee/ankle. Heights matched the anatomical fractions (0.80/0.60/0.46/0.50/0.27/0.05 H) to within a percent, but the sideways offsets - how far an A-pose spreads the arms, how wide the stance is - are what actually vary, and those are measured. `art/pipeline.py` encodes the whole process so the remaining roster is one call each.
- **Three bugs found by measuring rather than guessing:** (1) Rodin's `bbox_condition` *stretches* the model to the requested ratio - asking for 1:1:2.4 produced a cone, not a tall humanoid. (2) Auto-weighting failed for **every** bone (100% unweighted) because the GLB had 11,717 duplicate vertices split along UV seams, so the mesh was not a closed surface and heat diffusion had no solution; welding at 0.0002 fixed it. (3) The transplanted sword rendered as a ~200-unit girder because `animateWeapon` owns `userData.weapon`'s scale and silently overwrote the counter-scale - fixed with an intermediate holder group it cannot see.
- *Two more that would have been silent:* `addRimOutline` would have cloned the 23k skinned geometry into a plain Mesh - an un-skinned shell frozen in the bind pose at double the vertex cost (rigged characters now opt out entirely, which also looks better); and `disposeObject3D` only protected `.map` behind `keepMap`, so the first `disposeMesh()` would have blanked every other instance's normal and roughness maps.
- *Tests now serve the repo over HTTP.* `GLTFLoader` fetches with XHR and Chrome blocks XHR to `file://` as cross-origin, so under `file://` every model silently failed and the art assertions would have been quietly testing the procedural fallback.

### Arenas (Batches 26, 29)

- **Fairness first.** Audited all ten maps for 180-degree rotational symmetry. Six passed. **Skyreach Spire had both spawns at y=750 - the same side of the arena** - with its climbing tiers rising from only one of them, so one player started next to the contested high ground and the other across the map. Sundered Stair's staircase existed only on the west side. Overgrown Sanctuary and Skyward Temple each gave exactly one player a ramp onto the high ground. All four redesigned, themes kept.
- `rotSym()` makes symmetry structural rather than remembered: an author describes half an arena and gets a provably fair whole. Centre pieces are their own twin; ramps get `from`/`to` swapped in the copy, because rotating 180 degrees reverses the axis the slope climbs and otherwise the twin ramp descends into the floor.
- **Skyward Temple's central dais was unclimbable for half the roster.** Its side steps sat 142 units from the dais edge; clearing that needs the full ~43-frame airtime *and* a fast character - Kaelen covers ~145 units, Draven only ~81. The map's own documented "dais climbed via a ramp and low side platforms" simply did not work for slow characters. Now a 42-unit gap.
- *A stale comment corrected rather than left to mislead:* Overgrown Sanctuary claimed its 222-high wall was "comfortable Double Jump reach from the height-60 cover blocks (gap 162)". Only the HEIGHT gap is 162 - those blocks are 227 units away horizontally, so it is reachable from them by no jump at all. That is intended (it is a lane divider, not a perch), but the comment said otherwise.
- *A test that asserted the wrong thing, and was corrected instead of the maps.* A first version required dividers to be Double-Jump reachable; `index.html` defines them as "interior walls / lane dividers", so making six maps' sight blockers climbable would have defeated their purpose. `mapscheck.js` now asserts the opposite - that they stay **unclimbable**, so a divider cannot become a 26-unit-wide camping ledge over the lane it closes off.
- **Surface relief on every map.** Canvases 256 -> 512, and normal + roughness maps *derived* from each existing canvas rather than authored: the art already encodes relief as brightness (mortar is dark because it is recessed), so a Sobel gradient of luminance is a serviceable height field. All twenty surfaces gain relief at once and each map keeps its hand-drawn identity, which swapping in a few photographic textures would have flattened. The gradient sample **wraps** (a non-wrapping Sobel seams every tile boundary), derived maps are tagged `LinearEncoding` (a normal map is data, not colour), and each material gets its own texture object wrapping the shared canvas because `repeat` lives on the texture and a wall, a platform and the floor tile the same source at different densities.

### Weapons, the first-person arm, and lighting (Batch 28)

- *The blades were a flat `BoxGeometry` slab with a 4-sided cone glued on* - no taper, no cutting edge, no central ridge - so they caught light like a painted plank. The fix is shape: `bladeGeometry()` builds a **diamond cross-section** (two edges, a raised spine) from a list of cross-sections, giving four long faces at different angles to the light. Sword, dagger, hammer, scythe and gauntlet all rebuilt on it.
- *The first-person arm was one `BoxGeometry(3.4, 3.4, 11)`* - a bare stick in the character's flat body colour, on screen every frame of every match, and looking nothing like the armoured arm the same character now has in third person. Now a tapered forearm with a plated bracer, an armoured glove with knuckle plates, and a thumb over the grip.
- **Image-based lighting, and the bug that revealed why it was needed.** The rebuilt weapons use physically-correct metal (metalness 1.0), and a fully metallic surface takes its colour *entirely* from what it reflects - so with no environment map a polished steel blade renders **pure black**, which is exactly how the first sword screenshot came out. Metals need an environment, not a brighter base colour. `PMREMGenerator` builds one from the same sky gradient the player is standing under, so reflections match each arena's palette and change with the map; every rough surface gets soft ambient bounce for free.
- *A precedence bug worth remembering:* `new THREE.CapsuleGeometry ? A : B` constructs before it tests, and `CapsuleGeometry` does not exist until three r140 - so it threw inside `startRound` and produced a black screen with no console error at boot.

### The crush cinematic (Batch 27)

Arena Collapse used to end with both fighters squashed in place while still in first person, which made the most dramatic beat in the match the one you could see least: your own body is hidden from your own camera, so you watched a static wall texture while your health drained.

- Both players now leave first person for a side-on third-person shot of themselves pinned between two grinding slabs, each framed in their own half of the screen.
- **Each fighter gets their OWN pair of slabs, on that fighter's viewmodel layer.** The two are far apart when the walls slam, so a single shared pair cannot close on both - the first attempt put one pair at the arena centre and neither player had walls near them. The VM layers are the only ones a single camera sees privately.
- *Each rig also carries a stage floor and a back wall*, neither decorative: the arena's own floor has shrunk to nothing by the time the crush fires (that is what the collapse does), so without them the shot was two figures floating against empty sky.
- *Each half shows ONE fighter* - the camera enables its own body layer **and disables the opponent's**; without the second half of that swap both appeared in both halves, one behind the other. Both are turned to face the camera, overriding their last combat heading, which otherwise left them crushed in profile or from behind.
- **The squash was retuned hard.** The first pass drove the footprint to 12% and the height to 175%, which turned a detailed PBR character into a vertical needle - non-uniform scaling that extreme reads as rubber, not force. Now a mild compression (~70% / ~114%), with the violence carried by the walls stopping at body width, a brace pose, contact dust, judder on contact and rising shake. The squash is driven by how far the slabs have actually closed, so the body deforms in step with the thing deforming it.
- **A real leak, found by testing the exit rather than the entry:** both "Play Again" and "Return to Menu" disposed the boss and zone ring but left the crush running - slabs in the scene, both cameras stuck in third person, viewmodels hidden - because only `startRound()` reset it. One `resetCrush()` now serves all three.

### Where this arc stands

`smoke`, `mapscheck`, `crushcheck` and `batch24check` all green, zero console errors. New permanent suites: `mapscheck.js` (symmetry, reachability, dividers, spawns) and `crushcheck.js` (the cinematic end to end).

**Blocked:** the remaining thirteen characters. Every AI model source is credential-gated - the Rodin free trial ran out of funds mid-arc, Hunyuan3D points at a local server on :8081 that is not running, and Sketchfab and Poly.pizza both need API keys. PolyHaven works but supplies textures and HDRIs, not characters. The pipeline is proven end to end on Kaelen and `art/pipeline.py` reduces each remaining character to one call, so this is a credentials problem rather than an engineering one.

**Reasoned, not playtested:** every animation clip (they are hand-authored keyframes, never watched at 60fps by a human), the crush pacing and framing, the derived-normal strengths per surface, and whether the arena redesigns still play well as spaces rather than merely measuring as fair.

**Also worth knowing:** the game must now be served over HTTP. Opening `index.html` directly falls back to the old procedural meshes, because Chrome blocks the model fetch on `file://`.

## Batches 31-32 - From local split-screen to online peer-to-peer

The brief: remove local 2-player and mobile (archiving both), move to online play over PeerJS, and modernise the controls - WASD+arrows with A/D strafing, pointer-lock mouse look, left-click attack. Ordered ahead of the arena/character art work at the user's direction, on the reasoning that split-screen renders the scene twice per frame and is the performance ceiling that work would hit.

### Archived first (Batch 31)

`legacy/local-splitscreen.html` is a verbatim copy of the build immediately before the refactor, with its asset paths rewritten to `../` so it actually runs. Verified: served over HTTP it boots, loads `kaelen.glb` (1 model, 0 failures - which is what proves the path rewrite worked) and reaches a live FIGHT with no console errors. A working fallback, not a file that merely exists. What lives only there now: the two-viewport split-screen path, the two-panel HUD (including the trick of drawing shared centred elements twice with a +/- `VIRTUAL_W/4` translate so nothing lands on the seam), two 10-action binding sets on one keyboard, and the whole touch scheme.

### Controls (Batch 31)

- *A/D and Left/Right STRAFE now.* The right-hand vector is `(fy, -fx)`: with forward mapped to world `(fx, 0, fy)` and up +Y, `cross(up, forward)` is `(fy, 0, -fx)`, so that is genuinely screen-right.
- *Mouse look on pointer lock*, requested by clicking the canvas during a fight. Applied as a raw radian delta and deliberately **not** scaled by `dt` - mouse movement is already an absolute displacement, so scaling it makes sensitivity depend on framerate.
- *Mouse buttons are synthetic keys.* Left click and right click live in the same `keys`/`pressed` maps under the names `mouse0`/`mouse2`, so they flow through `consumePress` and the rebind UI unchanged instead of needing a parallel input path.
- *One binding set.* The two-side layout existed only to fit two players on one keyboard, which forced compromises that no longer apply - P1's jump had been moved off Space specifically because an oversized thumb key made P1 jumping easier than P2's. Jump is Space again, dash is Shift. Stored under a **new** localStorage key on purpose: the old value is a `{p1,p2}` blob whose action names (`up`/`left`) no longer exist, so merging it over the new defaults would silently produce a binding set with dead entries.
- *Keyboard pitch survives as a fallback* for when pointer lock is refused - mouse look is primary but must not be the only way to aim up at the high platforms Batch 20 made reachable.
- **Touch removed entirely (~18 KB).** It is fundamentally incompatible with one-player mouse look, so leaving it half-wired would have been a broken intermediate state. `TOUCH_UI` went with it, so antialias, shadows and pixel ratio are now unconditional.

### One view

`renderViews` always draws a single full-screen view from the local fighter's camera. Beyond being what online needs, this halves the scene render cost and removes the reason post-processing was impractical: an `EffectComposer`'s full-screen quad passes do not honour an outer scissor rect, so bloom would have needed one composer per half. **Your own health bar stays on the LEFT whichever side you are** - as the joiner you are p2, and having your own bar jump to the right-hand slot would be a pointless difference between the two clients.

### Netcode (Batch 32), and why it is not lockstep

The obvious reading of "send input packets and apply them to the opponent" is deterministic lockstep. That cannot work here, and it is written into the code so nobody tries:

- `dt` is **real elapsed time**, and every constant in the file is tuned in frame-units and multiplied by it. Two machines never produce the same `dt` sequence, so positions, cooldowns and turn angles diverge on the first frame.
- `hitStopFrames` skips the simulation entirely for a few frames on hit, driven by local damage events.
- Pausing is per-client and halts the whole simulation; `REDUCED_MOTION` changes the intro path.
- Per-side progression feeds `upgradeMult()` into fighter construction, so two clients with different local saves build **genuinely different stats for the same character**.

So: **peer state sync, each client authoritative for its own fighter.** Your fighter is driven by your input with zero latency; you broadcast its transform at 30Hz; the opponent is a puppet whose own physics is suppressed (running it would fight the incoming state - gravity pulling it down between packets, `resolveObstacles` shoving it out of geometry its owner stands in happily). The host owns match setup and the arena choice, and resolves "random" to a **concrete** map before broadcasting, or each side would roll its own.

**Hits are attacker-authoritative.** Whoever throws the swing decides on their own machine whether it landed and sends a `HIT`; the victim applies it to itself and its `hp` flows back in the next `STATE`. Damage is never resolved locally for an attack thrown by the remote fighter, and environmental damage (crush, burn) is applied by each client to its own fighter only - otherwise both land twice. A victim's dodge i-frames still beat an incoming networked hit, which favours the victim and is the less frustrating call.

Interpolation is a lerp toward the last received state, with a snap past 220 units. Not dead reckoning: this game teleports constantly (Kaelen's dash, Voss' blink, Nyx's pull, every dodge), and extrapolating through a teleport predicts confidently in the wrong direction, which looks far worse than arriving a frame late.

### Real bugs found by writing the test

- **`takeDamage(msg.dmg, null, true)` put the flag in the `dir` parameter.** So `fromNet` was undefined, the authority gate suppressed the very message it exists to let through, and **no networked hit would ever have landed.** The single most valuable thing the test caught.
- **`netTick` sent nothing when there was no local fighter** - which is the entire time you are on the menu, in the lobby, or picking a character. The peer heard silence, the 6-second drop timeout fired, and **the connection died before the match could start.** Sitting in a lobby for more than six seconds is completely normal. Fixed with a keepalive `PING`.
- **`togglePause` ignored `INTRO`**, so a disconnect during the drop-in cinematic left the match running against a puppet nobody was driving.
- Stale from the Batch 31 control change: the pause screen and tutorial still printed two identical control lines labelled P1 and P2.

### Test-environment findings worth recording

Roughly half the debugging time went on the harness, again:

- **Two tabs in one browser does not work for a two-client test.** Chrome does not run `requestAnimationFrame` in a background tab and only the last-created tab is foreground, so the host's game loop never ticked and it never sent a single packet. The `--disable-background-timer-throttling` family did not lift it in headless. Two separate browsers does work, and is what two real players have anyway.
- **The loopback relay cannot sustain 30Hz.** Every message is a CDP round trip, so the test starves the link and the (correct) silence timeout fires - which failed every later assertion for that one reason. The timeout is now a mutable field the checker raises, and it gets its own deliberate section instead of being tripped over.
- A wait that expires must be *reported*: four silent 40-second `waitInPage` timeouts turned one run into three minutes and made every downstream failure look like a netcode bug.

## Batch 33 - Mobile gets an honest answer, and the harness stops eating the machine

### The desktop build tells you to use a desktop

Batch 31 removed the touch control scheme along with split-screen. That left a
build that a phone can *load* and cannot *play*: aiming needs a mouse and moving
needs a keyboard, so someone tapping through the menu would reach a match where
nothing responds. A full-screen notice now says so on a touch device, above
`#cdn-error`'s z-index because "you need a computer" is the more useful message
than anything else that could be on screen.

Detection is the same test the old `TOUCH_UI` used - a coarse primary pointer
**or** no hover, **and** `navigator.maxTouchPoints > 0`. A touchscreen laptop
reports a fine pointer and real hover, so it is not caught. **"I have a mouse
and keyboard - continue" exists regardless**, because pointer media queries do
misreport on hybrid devices and being wrong here would lock someone out of a
game they can play perfectly well. Getting the detection wrong must not be
unrecoverable.

### The archived build is single-player on a phone

The notice offers the archived split-screen build, which still has full touch
controls - so it is a redirect, not an apology. But **split-screen on a phone is
not playable**: each player gets a ~195pt-wide viewport with a joystick and four
action buttons layered on top of it. Since a phone is exactly where someone
arrives from that notice, the archived build now forces P2 to a bot on a touch
device and **hides both bot toggles** - there is nothing to choose, and a
permanently disabled button answering a question nobody asked was the Batch 24
complaint.

**The restriction must not become a farming shortcut.** Bot mode is sandbox-only
precisely so coins cannot be farmed against an AI, so `MOBILE_SOLO` suppresses
coin awards the same way the sandbox does. Otherwise "open it on a phone" would
have been the cheapest way to buy the roster.

`MOBILE_SOLO` is declared up with the earliest state, **not** next to `TOUCH_UI`
where it thematically belongs, because `addCoins` and `refreshBotUI` both read
it during initial load and a `const` further down the file is still in its
temporal dead zone there. Fifth instance of this exact trap.

Two smaller things, both noticed while testing rather than designed: every
navigation between the two builds now carries `location.search`, so `?debug=1`
survives the trip; and the touch hint copy was rewritten, since telling someone
the screen splits left and right is now simply false.

### The harness was making the whole computer unusable

Reported as "commands are 10-20x slower and the machine is extremely laggy,
starting when you began the multiplayer update". It was the test harness, and
the timing was not a coincidence.

**Mechanism.** puppeteer shuts a browser down only when the script reaches
`browser.close()`. A run killed first - a timeout, Ctrl+C, an unhandled
rejection - orphans a complete Chrome with its renderer and GPU children, and
each orphan keeps rendering the game's 3D scene through **swiftshader, software
GL on the CPU**, at 1400x1000, indefinitely. `netcheck` launches **two** browsers
per run. 32 stray processes were observed at one point; a plain `grep` timed out
at 120 seconds and new launches began failing with "timed out waiting for the WS
endpoint", which reads exactly like a test bug and is not one.

**And I made it permanent myself, in this update.** To fix netcheck's background-
tab problem I added `--disable-background-timer-throttling`,
`--disable-backgrounding-occluded-windows` and `--disable-renderer-backgrounding`
to the *shared* `launch()`. Those flags exist to stop Chrome throttling hidden
pages - so every orphan that would otherwise have idled kept software-rendering
at full speed forever. That is the direct answer to "why did it start then".

Three fixes, in order of how much they matter:

- **The flags are opt-in now** (`launch({ keepAnimating: true })`), taken only by
  `netcheck`, which is the one checker that genuinely drives two clients at once.
  A blanket default made every leaked browser maximally expensive.
- **`browser.close()` on every exit path.** The harness tracks every browser it
  launches and closes them from `process.on('exit')` plus `SIGINT`/`SIGTERM`/
  `SIGHUP`/`SIGBREAK`, `uncaughtException` and `unhandledRejection`. Those
  handlers kill the process rather than awaiting a graceful protocol shutdown,
  because there is no time for one during exit.
- **`node tests/cleanup.js`** mops up strays that predate this, or a SIGKILL that
  runs no handlers at all. It matches on the **command line** (`swiftshader`,
  `--headless`), never on the process name: a blanket `taskkill /F /IM chrome.exe`
  closed real browser windows once, and every process this kills must be provably
  ours.

`smoke` and the new `tests/mobilecheck.js` (14 assertions) both pass under the
changed harness and leave zero strays behind - which is the actual regression
test for this fix.

### Also: settings can leave

Requested separately - Settings gains a link to the archived local split-screen
build, and that build has one back, so switching modes is not a one-way trip
through the URL bar. Both send a `BYE` and tear the peer connection down first
rather than leaving a half-open link behind.

select screen showed two symmetrical rosters when you can only ever pick one
fighter, `previewPick` silently refused every click on the other one, and
"Waiting for P2..." read as *a local second player is missing* rather than *a
person on another machine hasn't chosen yet*. The instruction was to pretend the
old version doesn't exist, and that is what this is.

**Home** is now a front page for the one thing this build does: Play Online, plus
Armory, How to Play and Settings. No mode button (the host picks the mode), no
difficulty, no sandbox.

**The room** replaces the select screen and is modelled on how online games
actually do this:
- a **connection bar** with the status pill and, for the host only, the room code
  and a Copy button - a joiner already typed it, so showing it back is noise;
- **two player slots**, yours accented and theirs observed, each showing the
  fighter, a portrait swatch in that fighter's accent colour, and whether they
  are locked in;
- **one roster - yours.** Both grids stay in the DOM (`buildGrid` and the
  keyboard dispatcher address them by id) but only the local side's wrapper is
  ever displayed, so a host and a joiner run byte-identical code;
- a **host-only Match Setup** column with the mode and arena, which the guest
  sees as a read-only summary.

**Connecting now takes you into the room.** Previously it left you on the front
page with a "connected" line inside a modal, and the only way forward was to
close it and work out for yourself that the screen underneath had changed
meaning.

### Four real bugs the redesign exposed

- **Your coins depended on whether you clicked Host or Join.** `progression` is
  keyed `p1`/`p2` - a split-screen artifact - and `LOCAL_SIDE` is `p1` when
  hosting and `p2` when joining, so hosting spent one save and joining spent
  another. Online there is one person at one keyboard and therefore one account:
  `prog()` now maps the local side to a single `ACCOUNT` slot, which fixes every
  downstream accessor at once (unlocks, upgrades, coins, `upgradeMult`).
- **Confirming your fighter started the match.** It auto-started whenever your
  confirm was the action that made both sides ready - which online means the
  match begins from whichever client confirmed *second*, bypassing the host's
  arena choice. The host's Start button is the only way in now.
- **The Rematch buttons restarted locally.** `startMatch()` with no broadcast,
  so the host dropped into a fresh arena while the guest sat on its game-over
  screen. Rematch now re-broadcasts a START like the first match, and is
  host-only; the guest is told what it is waiting for.
- **`goHome()` was not a teardown.** Leaving a room mid-match left the
  simulation running and the mode props (a co-op boss mesh, Zone Control's ring,
  a half-finished crush with both cameras in third person) in the scene behind
  the home screen. Batches 18 and 27 fixed exactly this for the other two
  exits; a third exit needed the same treatment.

### What was deliberately removed

- **The sandbox switch.** It was the only door to bot mode, and it was never a
  private setting: per-side progression feeds `upgradeMult()` into fighter
  construction, so one player flipping it brings a measurably stronger fighter
  into a real match. Still reachable under `?debug=1`.
- **Bots, and the difficulty cycler with them.** Online the opponent is a person.
  `p1IsBot`/`p2IsBot` survive because the Fighter constructor, the AI branch of
  `update()` and `beginMatch` all read them, and the archived build uses them.
- **The two co-op modes, from the mode list.** Their enemies are AI-driven and
  the AI is not networked - each client would simulate its own boss from its own
  frame timing and they would diverge on the first hit. Shipping a mode that
  cannot work is worse than not offering it; they stay in the archived
  split-screen build, which Settings links to. The mode picker now offers the
  three versus modes.
- **17 dead CSS rules** for markup that no longer exists. Not tidying: a
  leftover `.menu-section button { width: 100% }` has broken two different
  features in this project, so dead selectors here are a live hazard.

### The tutorial was actively wrong

It taught turning instead of strafing, promised touch controls and a split
screen, explained Shop tabs that no longer exist, told you to enable a bot in a
sandbox that is gone, and documented two modes this build cannot run. Wrong
documentation is worse than missing documentation - someone reads it and then
cannot find the thing. Rewritten, with a new **Online Play** card.

## Batch 34, part two - photographic arena surfaces

The arenas were dressed entirely in 256x256 canvases painted at runtime, with
normal and roughness derived from their luminance. That is a good trick and it is
what made ten distinct arenas affordable - but hand-painted 256px albedo is the
single biggest reason they read as toy-like. Now: real 1k PBR sets from
PolyHaven (CC0), 11 of them, three files each - `Diffuse` (sRGB), `nor_gl`
(**GL** convention, not `nor_dx`, which has Y inverted and lights everything
backwards) and `arm` (AO+Roughness+Metalness packed in R/G/B, exactly the glTF
ORM convention three.js reads natively: one file, three slots).

Three things make it safe:

1. **It is an upgrade, not a replacement.** The procedural material renders
   immediately; the photo set is fetched asynchronously and swapped onto the
   *same* material when it arrives. A slow or failed fetch leaves a fully
   playable, fully textured arena. The game never waits on the network.
2. **Each map keeps its identity.** `theme.wallColor`/`floorColor` still tint the
   albedo, and the procedural canvas is kept as an **emissive overlay** -
   extracted by pulling out the accent-coloured pixels - so Voltaic Nexus keeps
   its glowing seams, Molten Foundry its lava cracks, the Colosseum its ivy.
   Dropping those would have flattened ten arenas into two rock textures.
3. **Textures are cached by tiling, never cloned per mesh** - see the leaks below.

**Columns were the last untextured thing** and, once walls and floors went
photographic, the only thing still reading as clay. They take the theme's *wall*
set, which is also correct art direction: a stone arena's pillars are cut from
the same stone as its walls.

### Three tuning mistakes worth recording, because each cost a render cycle

- **Tiling density is the most visible thing here.** The procedural canvases
  tiled every ~190 world units on the floor; a real 1k photograph at that
  density reads as one enormous slab - diamond plate came out looking like giant
  scoops. A fighter is 40 units wide, so the target is 45-55 units per tile.
- **`metalness: 1.0` renders walls near-black.** A fully metallic surface has no
  diffuse term; all its brightness is reflected environment, and this scene's
  environment is a PMREM of the sky gradient - dim, and mostly sky-blue. Floors
  face up into the bright part and look right; walls face sideways into the dark
  part and go black. `docs/arena-art-plan.md` recorded this from Batch 25 and it
  still caught us. Capped at 0.45.
- **Albedo choice beats tint.** `factory_wall` is *green* corrugated steel and no
  tint can take green out of an albedo; `metal_plate` is neutral but it is a
  dark brown *floor* plate whose tread reads as woven fabric at wall scale. The
  answer was a third set (`concrete_wall_003`, clean and bright) - and then
  raising the **fill light** from 0.4 to 0.85, because a photographic albedo is
  darker than a painted one and the fill is what lifts the walls' inward faces.
  Lighting, not albedo, decides how this scene reads. Third time that lesson has
  come up.

### Bugs fixed alongside, all from docs/arena-art-plan.md

- **The reported first-person arm defect.** `buildViewmodelArm` built the bracer
  as `CylinderGeometry(..., true)` - the trailing argument is **`openEnded`** - so
  it had no end caps and, with default `FrontSide` culling, you looked straight
  through the tube to the background. The elbow end is the nearest part of the
  model to the camera, so it was the first thing you saw, and it read as the arm
  being severed. Closed, and the limb is now long enough to run out of frame:
  a real first-person arm continues past the edge rather than stopping in
  mid-air.
- **The reported "special teleports with no animation".** Not lag.
  `teleportTo()` moves the fighter instantly and `render3D` copies the simulation
  position onto the mesh every frame, so every teleport was a one-frame jump *by
  construction* - Kaelen's Blade Dash, Voss' blink, Nyx's pull, Karrigos' charge,
  knockback and every dodge. `animateWeapon` *does* have dash and special cases,
  so the **arm animated while the body teleported**, which is why it read as
  broken rather than merely fast. Fixed with a visual-only lag offset that
  decays over ~6 frames plus a motion streak along the path: the simulation
  still moves in one frame, so i-frame windows, hitboxes and the AI's range
  checks are bit-identical.
- **The shadow frustum never followed the sun.** It was authored once as a fixed
  +/-1000 x +/-650 box for the default sun position; `applyLighting` then moved
  the sun per map, as far as (-2000, 1700, 1100), and never touched the frustum -
  so on maps with a low sun part of the arena silently stopped casting shadows.
  Now fitted by projecting the arena's world AABB into the light's own view
  space, so every map is correct by construction rather than tuned.
- **`fillLight.intensity` was never overridden** by any theme and sat at 0.4
  forever, so an overcast castle and a golden-hour desert got identical bounce.
- **Karrigos snapped from 1.5x to 1.0x the instant he started dying.**
  `renderDeathAnim` and the crush cinematic both *assigned* to `mesh.scale`
  rather than multiplying, discarding the per-character size multiplier the
  builders apply (Karrigos 1.5, Grint 0.72, Slagling 0.86, Hollowkin 1.08). It
  only ever self-healed because `initMesh()` builds a fresh group each round.
  Both now multiply a stored `meshBaseScale`.
- **Two texture leaks, one pre-existing since the art batches.**
  `buildPlatformMesh` and `buildOuterWall` cloned the wall canvas *per mesh*, and
  `attachSurfaceMaps` built two fresh `CanvasTexture`s *per material* - all
  landing on `keepMap` materials, which suppress texture disposal. So every
  `loadMap()` leaked a set per platform, per wall and per floor, for the life of
  the session. All of them are cached by tiling now, which is the correct
  granularity: the clone exists only because `repeat` lives on the texture
  rather than the material. **`tests/artcheck.js` asserts this directly** - load
  four arenas and require that revisiting one adds no textures - because a slow
  leak is invisible to every other assertion and to any screenshot.

### Testing

`tests/onlineuxcheck.js` is new: 40 assertions about the *shape* of the UI - how
many rosters are visible, who can start, who owns the arena, and what each
screen says is blocking progress. Every one of those would pass a "nothing
threw" test while still being the broken UI that was reported.

`tests/artcheck.js` is new: 16 assertions covering the photographic swap
actually happening, `uv2` present wherever the packed ORM's AO channel is used
(it samples `vUv2` in r128), encodings correct (colour sRGB, data Linear),
metalness capped, the accent overlay surviving, the texture leak, and the shadow
frustum genuinely refitting between two differently-lit maps.

Four existing checkers needed updating for the new UI, and it is worth being
explicit that these were **not** regressions - they asserted a screen that was
deliberately removed: `batch24check` (per-side shop buttons -> one Armory; the
bot-toggle section now asserts bots' *absence*), `controlscheck` (started its
match through the bot toggle; now hosts a room), `netcheck` (same bot section,
and `chooseMap` no longer starts a match).

`smoke`, `mapscheck`, `crushcheck`, `mobilecheck` pass unchanged - notably
`mapscheck`, since rotational symmetry and reachability are the properties most
at risk from arena work and this pass deliberately touched materials rather than
geometry.

**Still not playtested**, and worth saying plainly: the arena tiling densities,
the fill-light increase and the teleport smear duration are all reasoned first
passes. They look right in rendered frames; they have not been felt in a match.

## Where this arc landed

All ten planned batches (11-21) are in and pushed, each as its own commit with its own checker script. The nine-suite regression set (`progressioncheck`, `cheatcheck`, `doublejumpcheck`, `reachabilitycheck`, `pitchcheck`, `touchlookcheck`, `modescheck`, `coopcheck`, `bosscheck`, `survivalcheck`, plus the desktop/touch/pause drivers) runs green end to end, and — unlike every batch before this arc — the verification exercises **real game state through the real game loop** rather than only checking that nothing threw, thanks to the `?debug=1`-gated `window.ACDebug` handle added in Batch 12.

**Recurring lessons this arc kept re-teaching, worth reading before the next change:**
- **TDZ is this file's most common self-inflicted wound** — four instances across the arc (`shopSide`, `MATCH_MODES`, plus the historical `camera` and `geometryCache`). The rule is now explicit in comments: *anything the load-time menu build touches must be declared before it*, regardless of where it thematically belongs.
- **CSS specificity and the box model bite repeatedly.** `.menu-section button { width: 100% }` has now broken two different features (the bot toggle, then the shop buttons); `max-height: 90vh` on modal panels positioned against a *container* clipped content at both ends with nothing scrollable to reach it.
- **Lighting, not albedo, decides how something looks here.** The arenas are bright and the renderer tone-maps at exposure 1.1, multiplying a lit diffuse surface roughly 3x — a mid-grey reads as beige. Unlit `MeshBasicMaterial` is the only way to guarantee an on-screen colour (which is also why `addRimOutline`'s unlit shell can swamp a large body).
- **Screenshots catch what assertions can't, and vice versa.** The HUD-overlap bug, the co-op arena-collapse bug, and all three Karrigos material problems were only visible in a rendered frame; the impossible jump gap, the telegraph regression, and the projectile-liveness subtlety were only visible to a computed assertion.
- **When a check fails, suspect the harness first if the mechanism is sound.** Roughly half the failures in this arc were the test measuring at the wrong moment (after projectiles had despawned, before a KO was detected, against a match that had already ended) or pinning coordinates the simulation then moved.

**What still needs a human:** everything about *feel*. Boss HP pools and difficulty scaling, Zone Control's 45-second target, Time Attack's 3 KOs, coin prices and upgrade values, the Survival heal question above, Karrigos' proportions and palette, and whether the co-op modes are fun with two people on one keyboard — all reasoned first passes, none playtested.

## Verification checklist (run at the end of every batch)

Unchanged from the original brief — these all require an actual browser session (input, visuals, timing, a human on the other side of the bot) that this pass couldn't run. Left unchecked deliberately rather than self-assessed as done; see "Final status" above.

- [ ] No console errors across a full match, including death sequence and a rematch
- [ ] Identical behavior at 30fps, 60fps, and uncapped
- [ ] Ten consecutive rematches, no GPU memory growth
- [ ] Every character's attack/special/skill fires, connects, shows an effect
- [ ] Nobody spawns inside geometry on any of the four maps
- [ ] Teleports and knockback never place a fighter inside a pillar or platform
- [ ] Correct winner declared, including when the winner is hit during the death sequence
- [ ] Bot plays a competent match against every character on every map
- [ ] Menu, pause, and gameover screens reachable/escapable by keyboard alone
- [ ] Window resize mid-fight doesn't shift hitboxes or break the HUD
